# requirements

## 背景・目的

現行の `/refactor-check` はコード品質・保守性の観点に強く、UI/UX の改善余地を体系的に抽出する用途には最適化されていない。
本作業では、UIコードを主対象とし、最新のUIトレンドとユーザー視点の使いづらさを同時に点検できる
「UI/UX改善提案プロンプト」の要件を定義する。

あわせて、既存仕様との整合を守るために以下を前提とする。

- チーム分割ロジック（10人条件、評価重み、JSON互換性）は変更しない
- API契約を無断で変更しない
- 提案は実装候補の列挙に留め、実装は `/implement` の責務とする

## ユーザーストーリー

- プロダクト改善担当として、UIコード中心の改善候補を一覧化したい。なぜなら見た目と操作性を継続改善したいから。
- エンドユーザー視点の開発者として、操作導線や文言の分かりづらさを早期に発見したい。なぜなら離脱や入力ミスを減らしたいから。
- レビューアとして、改善提案に優先度と根拠がほしい。なぜなら実装順序を合意しやすくしたいから。
- 実装担当として、提案が既存仕様を壊さない条件つきで提示されてほしい。なぜなら回帰リスクを抑えて着手したいから。

## 受け入れ条件

### 正常系

1. `.github/prompts/` に UI/UX改善用プロンプト（例: `ui-ux-check.prompt.md`）の要件が定義される
2. プロンプトの主な調査対象として `components/`, `pages/`, `pages/api/`, `composable/`, `utils/` が明記される
3. 出力形式に以下が含まれる
   - 問題点（現状）
   - ユーザー影響（誰にどんな不便があるか）
   - 改善案（具体案）
   - 実装コスト見積もり（S/M/L）
   - 優先度（High/Medium/Low）
4. 提案項目は「UI実装改善」「UX改善」「仕様影響あり（要件化推奨）」の区分で整理される
5. UIトレンド観点（情報設計、操作導線、視認性、フィードバック、モバイル配慮、アクセシビリティ）が
   チェック観点として明記される
6. 既存仕様と衝突する提案は「実装しない」ではなく「別 `.steering` で要件化」として扱う方針が定義される
7. チーム分割の不変条件（参加者10人、評価式重み、`fromJson`/`playersInfo` 互換性）を
   変更対象外として明示する

### 異常系

1. UI改善提案がドメイン仕様変更を必要とする場合、即時実装対象から除外して要件化へ誘導する
2. APIレスポンス契約の変更が必要な提案が出た場合、`docs/team-balancer.v1.yaml` 更新が必須であることを
   警告として出力する
3. 根拠が曖昧な提案しか出せない場合、該当項目を「要再調査」として分離する
4. 変更範囲が大きすぎる場合、段階導入（フェーズ分割）の提案を必須とする

## 問題点リスト（UI/UX改善候補の反映）

### High

1. `pages/index.tsx`（要調査）
   - 課題: 主要CTA（分割実行/保存/復元）の優先度が視覚的に不明確
   - 区分: UI実装改善
   - 影響: 操作迷いと誤操作により完了時間が増加
   - 改善方針: Primary/Secondary/Destructive を Tailwind で明確化し、1画面1主目的に統一
   - 見積もり/判定: S / 即時対応可
2. `components/*`（要調査）
   - 課題: 入力エラー表示位置と再試行導線が弱い
   - 区分: UX改善
   - 影響: 入力やり直しコスト増、離脱率増
   - 改善方針: フィールド直下エラー + 画面上部要約 + エラー項目へフォーカス移動
   - 見積もり/判定: M / 即時対応可
3. `pages/api/*` + `composable/api.ts`（要調査）
   - 課題: 通信中/失敗時の状態可視化不足
   - 区分: UX改善
   - 影響: 多重クリック、重複送信
   - 改善方針: ボタン無効化、進行表示、通知、再試行導線の統一
   - 見積もり/判定: M / 即時対応可

### Medium

1. `components/*`（要調査）
   - 課題: ラベル/補助説明/必須表示の一貫性不足
   - 区分: UI実装改善
   - 影響: 初見ユーザーの入力ミス増
   - 改善方針: フォーム部品共通化で表示パターン統一
   - 見積もり/判定: M / 即時対応可
2. `pages/*`（要調査）
   - 課題: モバイル時の操作完了性不足（スクロール量・ボタン到達性）
   - 区分: UX改善
   - 影響: モバイル完了率低下
   - 改善方針: 主要操作の固定表示やセクション順再設計
   - 見積もり/判定: M / 即時対応可
3. `components/*`（要調査）
   - 課題: キーボード操作・フォーカス可視性の不足
   - 区分: UI実装改善
   - 影響: アクセシビリティ低下、誤操作増
   - 改善方針: `focus-visible` の統一、Tab順、Enter/Escape 動作整理
   - 見積もり/判定: S / 即時対応可

### Low

1. `pages/index.tsx` + `docs/team-balancer-spec.md`（要調査）
   - 課題: 用語の平易化不足（ドメイン語の言い換え）
   - 区分: UX改善
   - 影響: 初回利用時の離脱
   - 改善方針: マイクロコピー簡潔化、補足ツールチップ追加
   - 見積もり/判定: S / 即時対応可
2. `pages/api/*` + `docs/team-balancer.v1.yaml`（要調査）
   - 課題: エラーコード体系の拡張が未整備
   - 区分: 仕様影響あり（要件化推奨）
   - 影響: 失敗理由が曖昧で復帰しにくい
   - 改善方針: APIエラー契約（`code`/`message`）標準化を別要件として検討
   - 見積もり/判定: L / 要件化推奨

## 受け入れ条件（追補: 今回追加分）

### 正常系（追補）

1. 上記のHigh/Medium/Low候補が `requirements.md` / `design.md` / `tasks.md` で同一粒度で追跡可能である
2. 「即時対応可」と「要件化推奨」がタスク上で分離され、実装順序が明確である
3. ファイル行番号未確定の項目は「要調査」を明示し、実装前に特定手順を持つ

### 異常系（追補）

1. API契約変更を伴う候補を即時実装タスクへ混在させない
2. 見積もり `L` 候補は `/requirements` 再起票対象として扱う

## スコープ外

- `utils/`, `components/`, `composable/`, `pages/api/` の実装変更
- テストコードの追加・修正
- 既存 API 仕様の実変更
- `/implement` 相当の実装実行
