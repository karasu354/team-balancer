# design

## アーキテクチャ概要

UI/UX 一新は、次の3段構成で進める。

1. 議論フェーズ（方針合意）
   - 画面課題の棚卸し
   - 体験方針（情報設計、視覚ルール、操作導線）を合意
2. 試作フェーズ（全面プロトタイプ）

- Copilot に UI コードの全面案を生成させる
- 比較用として差分を確認し、採用 / 不採用 / 保留を評価する

3. 実装フェーズ（部分採用で段階反映）
   - UI基盤の統一（見出し、余白、ボタン、状態表示）
   - 主要画面（入力・一覧・分割結果・保存/復元）の導線改善
   - テストとドキュメントで回帰防止

## 影響ディレクトリと責務分離

- `components/`
  - 入力フォーム群、一覧、結果表示の UI/UX 改善
  - 単一責務を保ち、必要に応じて分割する
- `pages/`
  - ページ全体レイアウト・セクション順序・コンテナ構成の調整
- `utils/`
  - 原則変更しない（必要最小限の表示補助のみ）
- `composable/`
  - API呼び出しは既存責務維持（UI刷新目的での仕様変更はしない）
- `test/`・`e2e/`
  - UI変更に伴う表示/導線差分を検証するテストを更新
- `docs/`
  - 画面仕様や運用手順に変更があれば反映

## データモデル・型定義の変更点

- 原則、既存型を再利用する
- `Player` / `TeamBalancer` / `PlayersJson` の契約は維持する
- UI状態の追加が必要な場合は、表示専用の局所状態として管理しドメイン型へ混入させない

## API変更有無と `docs/team-balancer.v1.yaml` への影響

- 本作業は UI/UX 改善が主目的のため、API変更は原則なし
- APIの入出力を変更する場合のみ `docs/team-balancer.v1.yaml` を更新する

## 既存の `fromJson` / `playersInfo` 互換性への影響

- 互換性に影響を与えないことを前提とする
- 影響が発生する案は今回対象外として別 `.steering` に分離する

## 実装方針メモ

- 議論結果は「採用案」「不採用案」「判断理由」を残す
- 試作フェーズでの全面差分は比較材料として扱い、本番反映は部分採用を原則とする
- 採用判断は次の観点で行う
  - 見やすさ（情報密度・可読性）
  - 導線（次操作の分かりやすさ）
  - 実装/保守コスト
  - 既存仕様との整合（10人条件・評価ロジック・保存復元）
- デザイン一貫性のため、Tailwind ユーティリティの使用方針を統一する
- 実装は小さな単位で段階的に進め、各段階で `format/test/e2e` を実行する

## 追加フィードバック反映方針（2026-05-03）

プレイヤー編集導線の改善案は、次の比較で決定する。

- 案A: 既存カード編集の高速化（矢印展開を自動化 / Editを1クリック化）
- 案B: 一括編集専用タブを追加し、全プレイヤーを連続編集できるようにする
- 案C: モーダル編集（一覧から対象選択→モーダルで編集）

現時点の採用方針（best）:

- 案Bを採用する
  - 理由1: 複数プレイヤーを続けて修正するユースケースに最短で対応できる
  - 理由2: 既存カードUIを残しやすく、回帰リスクを抑えやすい
- 既存カード編集導線は並行提供して段階移行する

保存/復元の配置方針:

- 「開始時/終了前」に使う前提に合わせ、ページ上部（ヘッダー直下またはヘッダー内）へ移動する
- 入力・一覧・分割より先に視認できる順序にする
