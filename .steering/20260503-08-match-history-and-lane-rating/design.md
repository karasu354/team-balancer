# design

## アーキテクチャ概要

既存の保存復元フローを維持しつつ、チームデータに履歴情報を追加する。

- 保存時
  - 試合結果確定APIで履歴1件を append
- 復元時
  - 既存のプレイヤー一覧に加え、履歴配列を返却
- 互換
  - 旧データに履歴がなくても、読み込み時に補完

## 影響ディレクトリと責務分離

- utils/
  - teamBalancer: 結果確定時の更新ロジック呼び出し点
  - 新規候補 history: 履歴エントリ生成、互換補完、削除時の再計算
  - 新規候補 rating: 履歴再生ベースの総合レート再計算
- components/
  - DividedTeamTable: 勝敗確定UIの入口
  - 新規候補 MatchHistoryPanel: 履歴一覧表示（案A）
  - 新規候補 MatchHistoryAccordion: 履歴詳細表示（案B）
  - PlayersTable / PlayerCard: 一覧での現在レート表示（控えめトーン）
  - PlayerEditCard: ティア/ランク更新時のレート自動再計算の表示ルール
  - 既存UI全般: 英語ラベルの日本語化・表記統一
- composable/
  - api: 結果確定・履歴削除エンドポイント呼び出し
- pages/api/
  - teams/[id]: 既存GET/PUTに加え、履歴削除と再計算の責務を検討

## データモデル・型定義の変更点

既存 PlayersJson を拡張する。

- 追加: PlayersJson に matchHistories を追加

  - id
  - playedAt
  - winnerTeam
  - teamsSnapshot
  - playerResults
  - ratingChanges

- 追加候補: ratingBaseline
  - 履歴再生の起点となるプレイヤー別基準レート
  - 任意履歴削除時の再計算で利用する

補完ルール。

- matchHistories が未存在の場合
  - 空配列で初期化

## API変更有無と docs/team-balancer.v1.yaml への影響

API変更あり。

- 既存 GET /teams/{id}
  - 返却型に matchHistories が追加される
- 既存 PUT /teams/{id}
  - 保存ボディに matchHistories を許容
- 追加候補 POST /teams/{id}/matches
  - 勝敗確定時の専用API
  - サーバー側で履歴追加を一括実行
- 追加候補 DELETE /teams/{id}/matches/{historyId}
  - 指定履歴を削除し、残存履歴をもとにレートを再計算する

専用APIを採用する理由。

- 履歴保存を1トランザクション相当に扱いやすい
- クライアントの更新責務を減らし、整合性を維持しやすい
- 履歴削除と再計算をサーバー側に集約できる

## 既存の fromJson / playersInfo 互換性への影響

- fromJson
  - 追加フィールドが欠損でも読み込める後方互換実装が必要
- playersInfo
  - 既存形式を壊さない
  - matchHistories は追加情報として扱い、既存参照箇所への影響を最小化

## ラベル日本語化方針

- ハードコード済み英語ラベルを洗い出し、日本語または文脈に合う短い表示へ統一する。
- 直訳しにくいラベルは操作意図ベースで再命名する。

候補例。

- Cards -> プレイヤー一覧 または カード表示
- Bulk Edit -> 一括編集
- Fixed -> 固定
- Desired -> 希望
- Participating -> 参加中
- Single -> 個別入力
- Multi -> 複数入力
- Team ID -> チームID
- Divide Teams -> チーム分け
- person mismatch -> 人数ミスマッチ または 人数差

## 履歴記録仕様（初期案）

- 1履歴で保持する情報

  - 試合日時
  - Blue/Red のチーム構成
  - winnerTeam
  - playerResults（各プレイヤーの win/lose）
  - ratingChanges（各プレイヤーのレート増減）

- playerResults の生成ルール

  - winnerTeam が blue の場合、blue 側プレイヤーは win、red 側プレイヤーは lose
  - winnerTeam が red の場合は逆

- ratingChanges の扱い
  - レーン別ではなく総合レートのみを対象とする
  - 算出は ELO レートベースとし、基本は「自分のレート」と「同レーン対面レート」から期待勝率を導出する
  - 追加要因として、チーム総合レート差、BOT/SUP は2人合算レート差の補正を検討対象とする
  - 採用した要因と係数は utils の定数として定義し、テストで追跡可能にする
  - 表示用の差分値は履歴確定時、または履歴再計算時に導出する

## プレイヤー編集時のレート同期ルール

- デフォルト方針は「ティア/ランクをレートの正とする」。
- `Player` の `tier` / `rank` 更新時は `setCalculatedRating()` を通じてレートを自動再計算する。
- 将来、手動レート入力を導入する場合は、手動固定フラグで自動再計算と排他にする。

## 履歴削除とレート再計算方針

- 採用方針: 差分巻き戻しではなく、基準レートからの再生方式を採用する。
- 削除フロー:
  - 指定履歴を event 列から除外する
  - `ratingBaseline` を起点に残存履歴を古い順に再生する
  - 各履歴の ratingChanges と現在レートを再構築する

この方式を採用する理由。

- 任意時点の履歴削除でも一貫した結果を得やすい
- 部分更新による壊れた状態を避けやすい
- テストで再現性を担保しやすい

## 表示設計方針

- 履歴表示

  - 採用決定: 案A（時系列リスト）+ 案B（詳細アコーディオン）
  - 一覧1件選択で、その行の直下に詳細アコーディオンを展開する
  - 一覧に表示する試合日時は秒まで表示する（YYYY/MM/DD HH:mm:ss）
  - 一覧行の補助情報は最小化し、「ミスマッチ」「勝ち数」「負け数」は表示しない
  - 詳細は左に Blue、右に Red の2カラム構成とする
  - 各プレイヤー行に勝敗、変動後レート、レート変動を併記する
  - レート表示は「変動後のレート（変動値）」形式で統一する

- プレイヤー一覧表示
  - プレイヤー名やロール情報を主情報として維持しつつ、現在レートを補助情報として表示する
  - 視覚的ノイズを抑えるため、文字サイズは小さめ、文字色はサブテキスト色を使う

## 方針変更メモ（2026-05-03）

- レーン別レート更新は今回スコープから除外する。
- 履歴詳細の深掘りは一覧内アコーディオンUIで実装する。

## UI改善方針（2026-05-03 追加）

### 履歴一覧のレイアウト制約

- `MatchHistoryPanel` の一覧コンテナに `max-height` を設定し、件数増加時は内部スクロールへ切り替える。
- これにより、履歴セクションが無限に縦伸びして他セクションを押し下げる挙動を防ぐ。

### 履歴行の連続表示

- 既存のカード型（行間あり）を見直し、行間をなくした連続リスト表示に変更する。
- 行の区切りは余白ではなく `border` を使って視認性を確保する。

### OP.GG 参考デザイン指針

- 一覧1行で主要情報を把握できる情報密度を優先する。
- 勝敗は背景色・テキスト色で即時判別できるようにする。
- 要素の優先順位は「勝敗 > 日時 > mismatch と win/lose サマリ」とする。
- 詳細はアコーディオンで表示し、一覧はスキャン性重視とする。

## E2E 実行設計（2026-05-03 追加）

- Fast E2E は「アプリケーション単体の挙動確認」を目的とし、外部依存はモックする。
- `/api/teams/*` に依存する保存/読み込みシナリオは、Playwright の route モックで Redis 依存を排除する。
- Integration E2E（`@integration`）のみ実 Redis 接続を許可し、`REDIS_URL` を必須にする。
- CI のデフォルトゲートは Fast E2E とし、Integration E2E は手動ワークフローで分離運用する。
