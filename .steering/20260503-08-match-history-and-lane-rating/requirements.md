# requirements

## 背景・目的

現行アプリは、分割時点のチーム構成を作る機能は充実している一方で、試合後の結果の記録粒度が不足している。
そのため、後から「誰が勝者側だったか/敗者側だったか」を振り返りにくく、運用知見が蓄積しづらい。

本機能の目的は次の7点。

1. チーム構成と試合結果を履歴として保存し、同一IDから再取得できるようにする
2. 履歴1件ごとに、プレイヤー単位の勝敗情報（誰が勝った/負けた）を保持できるようにする
3. 英語UIラベルを、ユーザーにとって自然な日本語または文脈に合った表示へ統一する
4. 履歴の修正や削除が必要になった場合でも、レート整合性を保ったまま運用できるようにする
5. レート変動を ELO レートベースで算出し、算出要因を明確化する
6. プレイヤー一覧から各プレイヤーの現在レートを控えめに確認できるようにする
7. プレイヤー編集時の「ティア/ランク」と「レート」の同期ルールを明確化する

前提として、保存は既存のチーム情報IDを用いた方式を維持する。

## ユーザーストーリー

- 友人グループの主催者として、試合ごとのチーム構成と勝敗を保存したい。なぜなら次回の調整や振り返りに使えるから。
- 友人グループの主催者として、各プレイヤーが勝者側/敗者側のどちらだったかを確認したい。なぜなら結果の振り返りを正確に行いたいから。
- 友人グループの主催者として、UIの英語表記を自然な日本語で読みたい。なぜなら参加者に説明しやすく、誤解を減らせるから。
- 友人グループの主催者として、履歴を誤登録したときに削除したい。なぜなら過去データの修正で現在レートが壊れてほしくないから。
- 開発者として、既存の保存復元互換を壊さずに履歴機能を追加したい。なぜなら既存利用者のデータをそのまま扱いたいから。

## 受け入れ条件

### 正常系

1. 試合結果確定時に、以下が1履歴として保存される

   - 試合日時
   - Blue/Red のチーム構成
   - 勝敗結果
   - プレイヤー単位の勝敗結果（win/lose）

2. 保存済みIDを読み込むと、最新プレイヤー情報に加えて履歴一覧も取得できる
3. 参加者10人条件など既存分割条件は変更しない
4. 履歴一覧の1行をクリックすると、その場でアコーディオン形式の詳細を開き、勝者/敗者の内訳を確認できる
5. 履歴の試合日時は秒まで表示される（例: YYYY/MM/DD HH:mm:ss）
6. 履歴詳細では、左に青チーム、右に赤チームのプレイヤー一覧を並べて表示できる
7. 履歴詳細では、各プレイヤーのレート数値（変動後）とレート変動を表示できる
8. レート変動は ELO レートベースで算出される

- 計算の基本対象は「自分のレート」と「同レーン対面プレイヤーのレート」とする
- 追加検討要因として、チーム総合レート差、BOT/SUP レーンの2人合算レート差を扱う
- 採用した要因と重み（または係数）は、設計とテストで追跡可能な形で定義する

9. プレイヤー一覧では、各プレイヤーの現在レートを主情報を邪魔しない控えめな見た目で表示する
10. プレイヤー編集でティア/ランクを更新した場合、レートはティア/ランクから自動再計算される

- デフォルト運用は「ティア/ランクがレートの正」とする
- 将来、手動レート入力を導入する場合は「手動固定フラグ」などで自動再計算と排他にする

11. 英語ラベルは文脈に応じて自然な日本語または統一表記へ置き換える

想定対象ラベル例:

- Cards
- Bulk Edit
- Fixed
- Desired
- Participating
- Single
- Multi
- Team ID
- Divide Teams
- person mismatch

表示方針:

- 機械的な直訳ではなく、画面文脈に沿った自然な表現を優先する
- 同じ概念は全画面で同一表記に寄せる
- ボタン文言、見出し、補助テキストで語調を揃える

12. 履歴一覧から任意の履歴を削除できる
13. 途中の履歴を削除した場合でも、削除後に残る履歴列を基準にレートを再計算し、現在のレート整合性を維持できる

### 異常系

1. 勝敗が未選択の状態では結果確定できず、検証エラーを返す
2. 履歴保存に失敗した場合、部分的な結果確定状態を残さない
3. 旧形式データを読み込んだ場合でも、欠損項目は初期化して処理継続できる
4. 不正な履歴データを受け取った場合、400系エラーを返す
5. 履歴削除またはレート再計算に失敗した場合、削除前のレート状態を維持し、部分更新を残さない

## 履歴表示の表示案と採用決定

- 案A: シンプル時系列リスト（採用）
  - 1行に日時、勝敗、勝者側チームを表示
  - 最小実装で導入しやすい
- 案B: 試合詳細アコーディオン（採用へ変更）
  - リストから1件選択で、その場に詳細を展開する
  - Blue/Red の両チーム比較を一覧文脈のまま見やすい
- 案C: プレイヤー軸フィルタ

  - プレイヤー名で絞り込み、担当レーンと勝敗推移を表示
  - 分析用途向けだが実装コスト高

- 案D: 削除時に差分巻き戻しを行う逐次更新方式
  - 実装は単純だが、途中失敗時の不整合や検証難度が高い
- 案E: 履歴をイベント列として再生し、基準レートから再計算する方式（採用）
  - 任意履歴削除時も整合性を保ちやすい
  - 再計算コストは増えるが、ロジックの正しさを担保しやすい

採用決定（2026-05-03）: 初期リリースは案A + 案Bを採用する。
削除とレート整合性の扱いは案Eを採用する。
案Cと案Dは将来検討または不採用とする。

## 方針変更メモ（2026-05-03）

- レーン別レート更新機能は、将来の拡張時にロジックが複雑化するため今回スコープから除外する。
- 履歴機能は「チーム構成 + プレイヤー単位の勝敗記録」を優先実装する。
- レーン別レート更新は除外したまま、総合レートの増減表示と履歴削除時の再計算は検討対象に含める。

## UIフィードバック反映メモ（2026-05-03）

- 履歴件数が増えても画面全体が縦に伸び続けないよう、履歴一覧コンテナに高さ上限と内部スクロールを設ける。
- 履歴行はカード間の余白をなくし、連続したリストとして表示する。
- 履歴一覧の視覚デザインは OP.GG の試合履歴UIを参考に、情報密度と可読性を優先する。

### 受け入れ条件（UI追加）

1. 履歴一覧は最大表示高さを超えた場合に内部スクロールへ切り替わり、ページ全体の縦伸びを抑制できる。
2. 履歴行どうしの上下余白はなく、連続した行として表示される。
3. 履歴行は OP.GG 参考デザインとして、勝敗が色で識別でき、主要情報を1行で確認できる。
4. 履歴行に表示する試合日時は秒まで表示する。
5. 履歴行の補助情報から「ミスマッチ」「勝ち数」「負け数」は非表示にできる。

### 受け入れ条件（追加UI/運用）

1. 履歴詳細はドロワーではなく、一覧行直下に開くアコーディオン形式で表示される。
2. アコーディオン詳細は青チームを左、赤チームを右に並べた2カラム構成とする。
3. レート変動が有効な場合、各履歴の詳細で増減値を確認できる。
4. 各履歴には削除操作があり、削除後は残存履歴をもとにレートを再計算できる。
5. 履歴詳細の各プレイヤー表示は「変動後のレート（変動値）」形式で確認できる。
6. プレイヤー一覧では各プレイヤーの現在レートを控えめな文字サイズ・文字色で確認できる。

## スコープ外

- レーン別レート管理
- ELO 以外のレート更新式導入（Glicko、TrueSkill 等）
- 履歴を使った自動再学習アルゴリズム
- 複数シーズン管理やシーズンリセットUI
- 履歴のグラフ可視化

## E2E テスト方針（2026-05-03 追加）

- 通常の E2E（`test:e2e` / `test:e2e:fast`）はアプリケーションスコープとする。
- 通常の E2E では外部依存（Redis など）に接続しない。
- 保存/読み込み系シナリオを含む API はモックで扱い、UI とアプリケーション挙動を検証対象とする。
- 実 Redis 接続は `@integration` タグ付きの Integration E2E に限定し、手動実行ワークフローで検証する。
