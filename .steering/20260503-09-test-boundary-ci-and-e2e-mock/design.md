# design

## アーキテクチャ概要

本作業はアプリ機能追加ではなく、テスト戦略と CI 運用の整合性を高めるための品質改善である。
境界線を以下の3層で再定義し、責務に応じてテストを配置する。

1. Unit（`test/utils`, `test/api`）

- 純粋関数・APIハンドラ単位の正しさを最短で検証する

2. Fast E2E（`e2e/*.spec.ts` かつ `@integration` 除外）

- ユーザー操作の主経路を Redis 非依存で検証する
- 保存/復元など外部依存は API モック/ダミー応答を使用する

3. Integration E2E（`e2e/*.spec.ts` の `@integration`）

- 実 Redis を使った保存/復元経路を検証する
- 手動 workflow で実行し、日常CIからは分離する

## 影響ディレクトリと責務分離

- `utils/`
  - 原則変更なし
  - 必要な場合はテスト補強に伴う最小リファクタのみ
- `components/`
  - 原則変更なし
  - E2E 安定化に必要な `data-testid` 等の最小追記のみ対象
- `composable/`
  - API 呼び出し境界のテスト容易性向上に必要な最小修正のみ対象
- `pages/api/`
  - Fast E2E のモック戦略と整合するレスポンス境界の明確化
- `e2e/`
  - Redis 非依存シナリオと Integration シナリオの棲み分けを明確化
- `.github/workflows/`
  - ローカル標準検証と CI 実行内容の対応を見直し、必要に応じてジョブ定義を最小調整
  - workflow ファイル名を責務ベースで再検討する（例: `test.yaml` -> `ci.yaml`）
  - `uses` の参照をタグからコミットハッシュへ固定し、供給網リスクを抑える
- `docs/`
  - テスト責務境界と運用手順の更新

## データモデル・型定義の変更点

- 原則として `PlayersJson` / `PlayerJson` など既存型を再利用し、APIモックの型乖離を防ぐ
- 新規ドメイン型の追加は行わず、必要ならテスト用ヘルパー型を `e2e/helpers` に限定して追加する

## API変更有無と `docs/team-balancer.v1.yaml` への影響

- API仕様の原則変更は行わない
- ただし、モック応答が既存 API 仕様から逸脱していた場合は、実装側を OpenAPI 定義へ合わせる
- API仕様を変更した場合のみ `docs/team-balancer.v1.yaml` を同時更新する

## 既存の `fromJson` / `playersInfo` 互換性への影響

- 互換性を維持する
- Fast E2E 用ダミーデータも既存 JSON 変換仕様を満たす形式で作成する

## 設計上の確認ポイント

1. 「どのテストで何を保証するか」をテストファイル単位で明示する
2. Fast E2E は外部依存ゼロで再現可能にする
3. CI で実行する内容はローカル標準手順で再現できる順序にそろえる
4. 重複テストは削減し、境界条件（10人条件、無効入力、APIエラー）は不足があれば追加する
5. `typecheck` は品質ゲートとして CI とローカルの双方で必須化する
6. ローカル/CI の共通セットは `npm run test:ci` として定義し、差分を最小化する
7. Fast E2E は Redis 非依存、Integration E2E のみ Redis 実接続という境界を workflow 変数でも明示する
