# requirements

## 背景・目的

現在のテスト運用は、ユニット/E2E/CI の責務境界がドキュメント上で分かれていても、
実際の変更時に「どこまでをローカル必須とするか」「Redis 依存をどこで検証するか」が曖昧になりやすい。

本作業では、日常開発で回すテストの境界線を明確化し、
GitHub Actions で実行する検証内容とローカル実行内容の整合を高めることを目的とする。
あわせて、Fast E2E では Redis 起動を前提にせず、ダミー値/モック応答で安定して通る状態を保証する。
また、`.github/workflows/` 配下のファイル名を役割ベースで再検討し、
`typecheck` を CI とローカルの両方で確実に実行する運用を明確化する。
さらに、GitHub Actions の `uses` は最新安定版のコミットハッシュへ固定し、
ローカルと CI で同一のテストセットを実行する。

## ユーザーストーリー

- 開発者として、ローカルで通した内容が CI でも同じ観点で通ってほしい。なぜならPR後の想定外失敗を減らしたいから。
- 開発者として、テストの責務境界（Unit / Fast E2E / Integration E2E）を明確にしたい。なぜなら追加・修正時の配置判断を迷わないようにしたいから。
- 運用担当として、Fast E2E は Redis なしで安定実行したい。なぜなら日次の検証速度と再現性を維持したいから。
- レビューアとして、テストカバーの不足や重複を判断しやすくしたい。なぜならレビューを仕様適合と回帰リスクの確認に集中したいから。

## 受け入れ条件

### 正常系

1. Unit / Fast E2E / Integration E2E の責務境界が文書化され、テスト追加時の判断基準がある
2. ローカルの標準検証手順と CI（GitHub Actions）実行内容の対応表があり、差分理由が説明される
3. Fast E2E 実行時に Redis 起動が不要であり、保存/復元系シナリオは API モックまたはダミー値で安定通過する
4. Integration E2E は `REDIS_URL` 前提の別経路として維持され、手動実行方針が明示される
5. テストの重複・不足観点から、削減候補（重複）と追加候補（境界ケース）が整理される
6. `.github/workflows/` のファイル名が責務に合う命名へ整理される（例: `test.yaml` の改名検討）
7. `typecheck` が CI で実行されるだけでなく、ローカル必須手順にも含まれる
8. ローカル/CI の共通テストセットを `npm run test:ci`（`format:test` + `typecheck` + `test` + `test:e2e:fast`）で実行できる
9. CI の Fast E2E は Redis 実接続を前提にせず、Integration E2E のみ Redis 実接続を前提とする
10. `.github/workflows/*.yaml` の `uses` はタグ参照ではなく、最新安定版に対応するコミットハッシュへ固定される
11. 変更後にローカルで `npm run format`、`npm run format:test`、`npm run typecheck`、`npm run test`、`npm run test:e2e:fast` が成功する

### 異常系

1. Redis 依存コードが Fast E2E 経路へ混入した場合、テストが失敗し原因が識別できる（モック漏れを検出できる）
2. CI とローカルの実行条件に差分がある場合、差分理由と代替検証手順をドキュメント化する
3. モック応答の型が実APIと乖離した場合、型チェックまたはテストで検知できる
4. 10人条件などドメイン制約を壊す変更があった場合、既存テストで回帰を検知できる
5. workflow ファイル改名で参照漏れや運用混乱が発生しうる場合は、移行手順を明記して段階移行する
6. `uses` のタグ更新時にハッシュ更新が漏れた場合、CI 設定レビューで検知できる

## スコープ外

- チーム分割ロジックの仕様変更（評価式や重み変更）
- `Player` / `TeamBalancer` の JSON 互換性を壊す変更
- 本番運用の Redis 構成変更
- 新規機能追加を主目的とした UI 改修
