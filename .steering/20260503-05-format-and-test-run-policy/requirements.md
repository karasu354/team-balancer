# requirements

## 背景・目的

現在、`npm run format:test` の実行有無や、実装後のテスト実行有無が開発者ごとにばらつくため、
フォーマット不整合や未検証の変更がPRに混入しやすい。

本作業では、以下を目的として運用を標準化する。

1. `npm run format:test` が常に通る状態を維持できるフローを定義する
2. コード実装・テスト実装の後に、必ずテストを実行する運用を明文化する
3. `npm run test` を共通入口として利用できるようにし、実行コマンドの迷いをなくす
4. PR 作成時に Description が自動で埋まらない問題を解決し、手入力を最小化する
5. PR 作成時のタイトル命名規則を再検討し、品質が安定する表現に統一する

## ユーザーストーリー

- 開発者として、実装後に何を実行すべきか迷わずに進めたい。なぜならPR前の品質確認を漏れなく行いたいから。
- レビューアとして、提出されるPRが最低限のフォーマット・テストを通過していてほしい。なぜならレビューをロジック確認に集中したいから。
- チーム運用者として、共通コマンドで検証手順を統一したい。なぜなら開発フローを再現しやすくしたいから。
- 開発者として、PR Description を自動生成して埋めたい。なぜならPR作成時の記載漏れを防ぎたいから。
- 開発者として、PRタイトルを適切な粒度と表現で統一したい。なぜならレビュー時に変更意図を即時に伝えたいから。

## 受け入れ条件

### 正常系

1. `package.json` に `npm run test` が定義され、標準の検証対象（少なくとも `test:unit`）を実行できる
2. `docs/copilot-workflow.md` に、実装完了時の必須実行順（`npm run format` → `npm run format:test` → `npm run test`）が記載される
3. `.github/prompts/implement.prompt.md` に、最終確認として上記コマンド順を必須化する記述がある
4. `.github/copilot-instructions.md` の PR前チェックリストに、`npm run format:test` と `npm run test` 成功条件が含まれる
5. 変更後に `npm run format:test` が成功する
6. PR 作成時の Description がテンプレートまたはプロンプト経由で自動生成される運用が定義される
7. PR タイトルの命名方針（例: Conventional Commits 準拠 + scope 指針）が再整理され、実例付きで明文化される

### 異常系

1. `npm run test` 導入が既存CI方針と衝突する場合、`npm run test` の実体（例: `test:unit` のエイリアス）を明示してドキュメント化する
2. フォーマット修正で意図しない差分が大量発生した場合、対象を分割して段階的に適用する方針を記録する
3. テスト実行に環境依存がある場合（Redis等）、`npm run test` の責務範囲と別コマンド実行条件を明記する
4. PR Description の自動生成が差分不足で不完全な場合、必須項目（背景/変更内容/テスト）を補完してから作成する
5. PR タイトルが曖昧な場合、scope と変更主語を明示した候補へ自動補正する

## スコープ外

- 新規機能追加（UI/API仕様の追加変更）
- Integration E2E の環境構築自体の改善
- CIワークフロー全体の再設計（本作業は既存方針の明確化が中心）
