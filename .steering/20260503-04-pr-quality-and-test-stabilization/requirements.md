# requirements

## 背景・目的

GitHub での PR 作成時に、タイトルと概要欄（Description）の品質が担当者ごとにばらつくと、レビュー効率が下がる。
また、現在失敗しているテストが残存すると CI が不安定になり、リリース判断が遅れる。

このため本作業では、以下を同時に整備する。

1. **目的（最優先）**: PR 情報を画一化し、誰が作成しても同じ品質になる運用を定義する
2. **目的（最優先）**: PR に必要な情報を整理し、レビューに必要な項目を漏れなく記載できるようにする
3. 失敗テストを分類・修正し、CI の成功状態を回復する
4. PR 作成時に Copilot/CLI を活用して、タイトル・概要欄の入力を可能な限り自動化する
5. format チェック（`npm run format:test`）を運用フローに組み込み、実行コマンドを明確化する
6. `.gitignore` を再検討し、テスト実行時に生成される不要ファイルを追跡対象から除外する

### PR に必要な情報（本要件で整理する対象）

- 背景（なぜこの変更が必要か）
- 変更内容（何を変更したか）
- テスト結果（何をどう確認したか）
- 影響範囲 / リスク（どこに影響しうるか）
- レビューポイント（重点的に見てほしい点）

### 品質維持のために運用へ追加する対象

- format チェックの実行タイミングとコマンド（`npm run format:test`）
- `.gitignore` の見直し基準（テスト・ツール実行時に生成される成果物）

## ユーザーストーリー

- 開発者として、PR タイトルと概要欄を迷わず作成したい。なぜならレビューアが変更意図を素早く理解できるようにしたいから。
- 開発者として、PR 情報を画一化したい。なぜなら担当者差による品質のばらつきを無くしたいから。
- 開発者として、失敗テストを優先度順に修正したい。なぜなら CI を安定させて安全にマージしたいから。
- レビューアとして、PR に必要な情報（背景、変更点、確認観点、影響範囲）が揃っていてほしい。なぜならレビューの抜け漏れを防ぎたいから。

## 受け入れ条件

### 正常系

1. PR タイトルのルール（Conventional Commits 準拠の要約方針）がドキュメント化されている
2. PR 概要欄テンプレート（背景 / 変更点 / テスト / リスク / チェックリスト）がドキュメント化されている
3. `/.github/prompts/commit-message.prompt.md` で `.steering` 単位の 1 commit ルールと整合した出力が可能である
4. 失敗テストがカテゴリ分けされ、修正計画と実施結果がタスクとして追跡できる
5. 最終的に CI で要求されるテスト（unit + e2e:fast）が成功する
6. PR 作成時に、タイトルと概要欄の初稿が自動生成される（人手修正は最小限）
7. PR 概要欄はテンプレートに沿って自動展開される（空欄を残さない）
8. PR の必須情報（背景 / 変更内容 / テスト結果 / 影響範囲 / レビューポイント）が常に含まれる
9. format チェックの実行コマンドと実行タイミングがドキュメント化されている
10. `.gitignore` の見直し方針と反映結果が明記されている

### 異常系

1. 失敗テストの原因が外部依存（Redis / 環境差分）の場合、再現条件と回避策が明記される
2. 修正対象が複数 `.steering` にまたがる場合、作業を分割する判断が記録される
3. API 仕様変更が必要になった場合、`docs/team-balancer.v1.yaml` 更新の要否が明記される
4. 差分情報が不足して自動生成精度が低い場合、必須追記事項（背景/変更点/テスト）を
   ユーザーに確認してから最終文面を確定する
5. format チェックで失敗した場合、修正手順（`npm run format` 実行など）が明示される

## スコープ外

- 新規機能追加（既存要件にない画面・API・ロジック追加）
- CI プラットフォームの全面移行
- Redis インフラ自体の構築・運用設計
- 外部 SaaS / GitHub App の新規導入を前提にした大規模運用変更
