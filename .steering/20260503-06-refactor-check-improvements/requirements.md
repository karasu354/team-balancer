# requirements

## 背景・目的

`/refactor-check` は改善候補の抽出に有効だが、現状は以下の課題がある。

- 抽出結果の粒度にばらつきがあり、実装につながる候補と将来対応候補の切り分けが曖昧になる
- 出力された候補をどこまで実際に対応するかの判断基準が明文化されていない

このため本作業では、次を同時に整備する。

1. `/refactor-check` プロンプトを改善し、優先度・根拠・改善案の再現性を高める
2. 実際に `/refactor-check` で抽出された候補のうち、機能変更を伴わない範囲を対応する
3. 対応方針（今すぐ対応 / 要件化して後続対応）の判断をドキュメントで明確化する
4. プロンプト責務の線引きを明確化し、`/refactor-check` は抽出、`/requirements` は要件化に限定する
5. 必要時のみ最新ベストプラクティスを参照できる外部参照モードを定義する（既定は無効）
6. `/implement` の最終確認に E2E 検証（少なくとも `npm run test:e2e:fast`）を含める
7. ドキュメント全体のテスト記載を監査し、unit / E2E / format の漏れをなくす
8. テストディレクトリ命名を `test/` または `tests/` のどちらかに統一し、方針を固定する

## ユーザーストーリー

- 開発者として、`/refactor-check` の出力をそのまま実装タスクへ落とし込みたい。なぜなら改善サイクルを速く回したいから。
- 開発者として、低リスクの候補は同一作業で対応したい。なぜならコード品質を継続的に上げたいから。
- レビューアとして、なぜ対応した/見送ったかを追跡可能にしたい。なぜならレビュー判断を明確にしたいから。
- 開発者として、プロンプトごとの責務境界を明確にしたい。なぜなら運用時の迷いと混在作業を防ぎたいから。
- 開発者として、必要なときだけ外部知見を取り込みたい。なぜなら再現性を保ちつつ改善の質を上げたいから。
- 開発者として、`/implement` 実行後の検証で E2E まで漏れなく確認したい。なぜなら PR 後の不具合流出を防ぎたいから。
- 開発者として、ドキュメント間でテスト手順が矛盾しない状態にしたい。なぜなら運用ミスを減らしたいから。
- 開発者として、テストディレクトリの命名を統一したい。なぜなら新規参加者の認知負荷を下げたいから。

## 受け入れ条件

### 正常系

1. `.github/prompts/refactor-check.prompt.md` に、抽出粒度と判定基準（優先度・根拠・改善案・対応可否）が明記されている
2. `/refactor-check` の出力形式に、実装可能性の判断情報（例: 即時対応可 / 要件化推奨）が含まれる
3. 抽出候補のうち、機能変更を伴わない項目が実際にコードへ反映される
4. 反映内容に対応するテストまたは既存テストで回帰が確認される
5. 実装後に `npm run format` → `npm run format:test` → `npm run test` が成功する
6. `refactor-check` で抽出件数や影響度がしきい値を超える場合、`requirements` へ自動誘導する条件が定義される
7. 外部参照モードは既定で無効とし、利用時のみ参照元・参照日・採用理由を記録するルールが定義される
8. `.github/prompts/implement.prompt.md` の最終確認手順に E2E（`npm run test:e2e:fast`）が含まれる
9. `docs/` と `.github/` の関連ドキュメントで、unit / E2E / format の記載漏れがないことを確認できる
10. テストディレクトリ命名は既存構成を優先して `test/` を正式採用し、移行方針を明文化する

### 異常系

1. 高優先度候補が機能変更に該当する場合、実装せず別 `.steering` で要件化する判断を記録する
2. 候補同士が競合する場合、影響範囲が小さい改善を優先する方針を記録する
3. 対応対象が多すぎる場合、優先度順に分割して段階実施する
4. 外部参照先が取得不可または情報の信頼性が低い場合、ローカル規約準拠の提案へフォールバックする
5. 外部知見が既存ルールと衝突する場合、既存ルールを優先し、衝突内容を記録する
6. ドキュメント監査で手順差分が見つかった場合、`copilot-instructions` を正とし他文書を同期する
7. `test/` と `tests/` が混在している場合、今回は `test/` を優先し `tests/` 新設を禁止する

## スコープ外

- 新機能追加や仕様変更を伴うリファクタリング
- チーム分割ロジックの仕様変更（10人条件・評価重み・JSON互換性に影響する変更）
- CI/CD ワークフロー全体の再設計
