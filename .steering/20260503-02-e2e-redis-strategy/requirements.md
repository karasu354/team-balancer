# 要件定義: E2E テストにおける Redis 取り扱い方針

## 背景・目的

現在の E2E テストは Playwright で実装済みだが、保存/復元シナリオが
`REDIS_URL` 依存のため、環境によってはテストがスキップされる。

この状態では、以下の課題がある。

- ローカル環境や PR で実行できるテスト範囲が不安定
- Redis 依存シナリオの実行タイミングが明確でない
- 失敗時に「アプリ不具合」と「環境未整備」の切り分けが難しい

目的は、E2E テストを以下の2レイヤーで運用可能にすること。

1. Redis 不要で常時実行できる Fast E2E
2. Redis 実接続で連携検証する Integration E2E

---

## ユーザーストーリー

1. 開発者として、Redis を起動していなくても主要な UI フローの回帰を検出したい。なぜなら、日常開発のフィードバックを速く安定させたいから。
2. 開発者として、保存/復元の実連携を実Redisで確認したい。なぜなら、本番経路の不具合を事前に発見したいから。
3. 開発者として、どのテストが環境依存かを明確にしたい。なぜなら、失敗原因を迅速に特定できるようにしたいから。

---

## 受け入れ条件

### 正常系

| # | シナリオ | 期待動作 |
|---|---|---|
| R-1 | Fast E2E を実行する | Redis 未起動でも主要 UI フロー（追加/分割/取り込み）が通る |
| R-2 | Integration E2E を実行する | Redis 接続で保存/復元シナリオが通る |
| R-3 | 実行モードを切り替える | 実行コマンドまたは環境変数で Fast/Integration を明示できる |

### 異常系

| # | シナリオ | 期待動作 |
|---|---|---|
| R-4 | Integration E2E 実行時に Redis が未設定 | テストは失敗理由を明示して終了する（黙ってスキップしない） |
| R-5 | Redis 接続失敗 | 失敗ケースが Integration テストとして判別できるログが残る |

---

## スコープ外

- Redis クラスタ構成や高可用性検証
- Redis の性能ベンチマーク
- CI ワークフロー全体の設計変更（別タスク）
