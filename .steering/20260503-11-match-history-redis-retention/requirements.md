# requirements

> 対象 steering フォルダ: .steering/20260503-11-match-history-redis-retention/

## 背景・目的

現行仕様では、試合結果確定時の戦績履歴は PlayersJson.matchHistories に保持され、
ID保存時に Redis へ保存される。
一方で、履歴保持件数に上限がないため、データサイズ増加・保存/復元時の転送量増加・
履歴UI描画コスト増加のリスクがある。

本タスクでは、既存の保存互換性を維持したまま、1チームあたり戦績履歴を最新50件に制限し、
運用時の安定性と応答性を高める。

矛盾の明示と採用方針:

- 要望には「戦績履歴も Redis で保存したい」が含まれるが、現行実装では既に保存されている。
- そのため本対応は「保存可否の追加」ではなく「保存データの保持上限(50件)の導入」を主目的とする。

## ユーザーストーリー

1. 利用者として、戦績履歴を保存しても直近の試合履歴を安定して参照したい。なぜなら、保存件数が増えても読み込みが重くならないようにしたいから。
2. 開発者として、履歴保持上限をドメインロジックで一元管理したい。なぜなら、UIやAPIで個別に制御すると不整合が起きやすいから。
3. 開発者として、既存データ形式との互換性を維持したまま上限導入したい。なぜなら、過去に保存済みの JSON を壊さずに運用したいから。

## 受け入れ条件

### 正常系

- 試合結果を確定して履歴を追加した際、matchHistories は常に新しい順で保持される。
- 履歴件数が50件未満の場合、既存動作と同じく履歴が追加される。
- 履歴件数が50件に達した状態で新規履歴を追加した場合、最新50件のみ保持される。
- ID保存( PUT /api/teams/{id} )後に復元( GET /api/teams/{id} )すると、保存済みの履歴件数は最大50件である。
- 履歴削除( DELETE /api/teams/{id}?historyId=... )後も、履歴再計算と整列規則(新しい順)が維持される。

### 異常系

- 古いデータで matchHistories が 51件以上含まれていても、読み込み時にアプリがクラッシュしない。
- 履歴削除対象が存在しない場合は既存どおりエラーを返し、上限導入によりエラー種別が変わらない。
- 10人ちょうどでない場合は既存どおり分割処理を実行しない仕様が維持される。

## スコープ外

- 上限件数を画面設定で変更できる機能の追加
- 勝敗確定フロー自体の UI 改修
- Redis キー構造(teams:{id}:players)の変更
- OpenAPI の新規エンドポイント追加

## 問題点リスト（リファクタリング観点の追記）

### 高優先度

1. API ルートへの責務集中
   - 対象: `pages/api/teams/[id].ts`
   - 問題: 入力検証、HTTP メソッド分岐、Redis 永続化、`TeamBalancer` 正規化が 1 ファイルに集約されている。
   - リスク: API 変更時の影響範囲が広く、保存仕様と HTTP 振る舞いが密結合になりやすい。
   - 採用方針: 入力検証、永続化変換、レスポンス組み立てを小さな関数へ分離し、正規化は `utils/` を唯一の正とする。

### 中優先度

1. `TeamBalancer` の責務拡大
   - 対象: `utils/teamBalancer.ts`
   - 問題: チーム分割、JSON 変換、戦績履歴保持、上限制御が同一クラスへ集まりつつある。
   - リスク: 将来の機能追加でクラスが肥大化し、テスト観点が増えて保守性が下がる。
   - 採用方針: 履歴正規化や保持上限判定を純粋関数として切り出し、`TeamBalancer` は集約点に留める。
2. Redis 接続設定の検証不足
   - 対象: `services/vercelRedis.ts`
   - 問題: `process.env.REDIS_URL` 前提でクライアント生成しており、設定不備の検出が遅延する。
   - リスク: API 実行時に 500 として表面化し、運用時の切り分けが難しい。
   - 採用方針: `REDIS_URL` を fail-fast で検証し、設定不備を早期検知できるようにする。
3. Redis キー命名の重複管理
   - 対象: `services/vercelRedis.ts`
   - 問題: `teams:${teamId}:players` がマジック文字列として直書きされている。
   - リスク: 保存対象が増えた際に命名揺れやキー衝突の温床になる。
   - 採用方針: キー生成関数または定数へ寄せ、命名規則を 1 箇所で管理する。

### 低優先度

1. API テストフィクスチャの重複
   - 対象: `test/api/teams-id.test.ts`
   - 問題: 保存/復元系テストで JSON フィクスチャ生成の重複が発生しうる。
   - リスク: 仕様変更時の期待値修正が散らばりやすい。
   - 採用方針: `test/` 配下にテストデータビルダーを用意し、共通化する。

## 追加ユーザーストーリー（保守性改善）

4. 開発者として、API ルートとドメインロジックの責務境界を明確にしたい。なぜなら、保存仕様の変更時に影響範囲を限定し、回帰を防ぎたいから。
5. 運用者として、Redis 設定不備を早く検知したい。なぜなら、本番で 500 エラーとして遅れて気づく状況を避けたいから。

## 受け入れ条件（保守性改善の追記）

### 正常系（追加）

- `pages/api/teams/[id].ts` では HTTP 入出力制御を主責務とし、履歴正規化の実処理は `utils/` 側の関数・クラスで一元化される。
- `services/vercelRedis.ts` では `REDIS_URL` 未設定または空文字を早期に検知できる。
- Redis キー生成規則は 1 箇所に集約され、保存対象追加時に既存キー命名規則を再利用できる。

### 異常系（追加）

- `REDIS_URL` が不正な場合でも、内部スタックトレースや機密情報を API レスポンスへ含めない。
- 履歴正規化ロジックを切り出しても、`fromJson` / `playersInfo` の互換性と 10 人条件は維持される。

## スコープ外（追記）

- Redis 保存値のスキーマ変更
- テスト戦略全体の見直しや E2E 構成変更
