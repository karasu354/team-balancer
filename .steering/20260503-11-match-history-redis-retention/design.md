# design

## アーキテクチャ概要

保持上限はドメイン境界である TeamBalancer に集約する。
履歴追加処理で最新50件に正規化し、その結果を既存の PlayersJson へ載せて Redis 保存する。
これにより、UI層や API ルート層で重複した上限制御を持たず、一貫した保存データを担保する。

加えて、今回の要件更新では API ルートの責務分離と Redis 接続設定の運用性改善を次段の設計対象に含める。
保存上限そのものは現行仕様のまま維持し、保守性改善を別タスクとして段階導入する。

## 影響ディレクトリと責務分離

| ディレクトリ | 変更方針                                                        | 責務                               |
| ------------ | --------------------------------------------------------------- | ---------------------------------- |
| utils/       | TeamBalancer の履歴保持上限定数と履歴追加時トリミング処理を追加 | ドメインロジックの正規化と互換維持 |
| components/  | 原則変更なし。必要時のみ表示件数前提の文言確認                  | 表示のみ、保存ルールは持たない     |
| composable/  | 変更なし                                                        | API 呼び出しラッパー               |
| pages/api/   | 変更最小。既存の PUT/GET/DELETE フローを維持                    | HTTP 入出力検証と永続化呼び出し    |

### 追加の責務分離方針

- `pages/api/teams/[id].ts`
  - HTTP メソッド分岐、リクエストバリデーション、HTTP ステータス返却を担当する。
  - `PlayersJson` の正規化や永続化前後の変換は補助関数へ分離し、ハンドラ本体を薄くする。
- `utils/teamBalancer.ts`
  - 履歴保持上限、履歴並び順、履歴正規化のドメインルールを唯一の正として保持する。
  - 将来的には履歴正規化関数を純粋関数として切り出し、`TeamBalancer` は集約点に留める。
- `services/vercelRedis.ts`
  - Redis 接続生成とキー命名規約の単一管理を担当する。
  - `REDIS_URL` の fail-fast 検証を導入し、設定不備を API 到達前または接続初期段階で検出する。
- `test/`
  - API テストのフィクスチャを共通化し、保存/復元仕様変更時の修正点を減らす。

補足:

- Redis保存責務は services/vercelRedis.ts だが、保持件数の正規化は utils 側で行う。

## データモデル・型定義の変更点

- PlayersJson の型定義自体は変更しない。
- MatchHistory の型定義自体は変更しない。
- TeamBalancer に履歴保持上限定数を追加する。
  - 例: MAX_MATCH_HISTORIES = 50
- finalizeMatchResult で履歴追加後に先頭50件へトリミングする。

追加方針:

- 履歴正規化に関する純粋関数を `utils/` へ抽出可能な構成にする。
- Redis キー生成は `teamId` を受けてキー文字列を返す関数へ集約する。
- 接続設定検証は `string | undefined` を安全に扱い、未設定を明示的にエラー化する。

## API変更有無と docs/team-balancer.v1.yaml への影響

- エンドポイント、HTTPメソッド、レスポンスコードは変更しない。
- スキーマ形状も変更しない。
- ただし運用上の制約として「matchHistories は最大50件」を仕様書へ明記する。
- OpenAPI の必須更新は軽微だが、description への上限注記を追加して仕様整合を取る。

今回の追記時点では API 仕様変更は想定しないが、実装時は以下を確認する。

- 責務分離のための内部関数抽出により API の入力必須項目やレスポンス形状が変化しないこと。
- `REDIS_URL` 検証追加により 500 の発生条件が明確化されても、外部公開されるエラーレスポンスの情報量は増やさないこと。

## fromJson / playersInfo 互換性への影響

- fromJson: 既存 JSON 読み込み互換を維持する。
  - 古いデータで 50件超の履歴を含んでいても読み込み可能。
  - 保存契機(finalize / PUT保存)で最終的に最大50件へ正規化される。
- playersInfo: 既存の返却形状を維持したまま、含まれる matchHistories の件数が最大50件になる。
- これにより JSON 変換 API の後方互換を壊さない。

追加互換方針:

- 履歴正規化処理をクラス外へ切り出す場合も、`fromJson` / `playersInfo` の公開契約は変更しない。
- Redis キー命名規則を集約しても既存の `teams:{id}:players` を維持し、保存済みデータの参照互換を壊さない。

## 仕様矛盾と採用方針

- 現行では既に戦績履歴を Redis に保存済みであるため、今回の主変更は保存有無ではなく保存上限の導入とする。
- 上限値はユーザー指定により50件を採用する。

## 実装方針・検証方針（追記）

### 実装方針

1. 既存の履歴保持上限 50 件は維持しつつ、保守性改善は後続タスクとして段階的に適用する。
2. API ハンドラの分割は公開インターフェースを変えず、関数抽出ベースで行う。
3. Redis 運用改善では、接続設定検証とキー生成集約を先に行い、挙動差分を局所化する。
4. テスト共通化は低優先度とし、主要仕様の回帰を防ぐ範囲に限定する。

### 検証方針

- API 単体テストで PUT / GET / DELETE のレスポンス形状とエラーコードが不変であることを確認する。
- `utils/` のユニットテストで履歴正規化関数切り出し後も 0 / 10 / 11 / 50 件の境界条件を維持する。
- Redis 設定不備時のテストでは、機密情報を露出せずに失敗を検知できることを確認する。
