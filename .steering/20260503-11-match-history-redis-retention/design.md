# design

## アーキテクチャ概要

保持上限はドメイン境界である TeamBalancer に集約する。
履歴追加処理で最新50件に正規化し、その結果を既存の PlayersJson へ載せて Redis 保存する。
これにより、UI層や API ルート層で重複した上限制御を持たず、一貫した保存データを担保する。

## 影響ディレクトリと責務分離

| ディレクトリ | 変更方針                                                        | 責務                               |
| ------------ | --------------------------------------------------------------- | ---------------------------------- |
| utils/       | TeamBalancer の履歴保持上限定数と履歴追加時トリミング処理を追加 | ドメインロジックの正規化と互換維持 |
| components/  | 原則変更なし。必要時のみ表示件数前提の文言確認                  | 表示のみ、保存ルールは持たない     |
| composable/  | 変更なし                                                        | API 呼び出しラッパー               |
| pages/api/   | 変更最小。既存の PUT/GET/DELETE フローを維持                    | HTTP 入出力検証と永続化呼び出し    |

補足:

- Redis保存責務は services/vercelRedis.ts だが、保持件数の正規化は utils 側で行う。

## データモデル・型定義の変更点

- PlayersJson の型定義自体は変更しない。
- MatchHistory の型定義自体は変更しない。
- TeamBalancer に履歴保持上限定数を追加する。
  - 例: MAX_MATCH_HISTORIES = 50
- finalizeMatchResult で履歴追加後に先頭50件へトリミングする。

## API変更有無と docs/team-balancer.v1.yaml への影響

- エンドポイント、HTTPメソッド、レスポンスコードは変更しない。
- スキーマ形状も変更しない。
- ただし運用上の制約として「matchHistories は最大50件」を仕様書へ明記する。
- OpenAPI の必須更新は軽微だが、description への上限注記を追加して仕様整合を取る。

## fromJson / playersInfo 互換性への影響

- fromJson: 既存 JSON 読み込み互換を維持する。
  - 古いデータで 50件超の履歴を含んでいても読み込み可能。
  - 保存契機(finalize / PUT保存)で最終的に最大50件へ正規化される。
- playersInfo: 既存の返却形状を維持したまま、含まれる matchHistories の件数が最大50件になる。
- これにより JSON 変換 API の後方互換を壊さない。

## 仕様矛盾と採用方針

- 現行では既に戦績履歴を Redis に保存済みであるため、今回の主変更は保存有無ではなく保存上限の導入とする。
- 上限値はユーザー指定により50件を採用する。
